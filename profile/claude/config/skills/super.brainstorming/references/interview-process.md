# The interview — from understanding the idea to presenting the design

Read this at the start of the Opening Phase, once research is dispatched. This is the conversation
guide: scope, the stack and framework forks, the understanding note, approaches, the design, and
work inside an existing codebase. How questions are chosen, ordered and asked — the decision tree,
the rounds, the lenses — is `./grilling.md`.

---

## The Process (expanded)

**Understanding the idea:**

- Run Research via Parallel Subagents first — all tracks dispatched in one turn, the same turn that asks the first question (or makes the companion offer); research never gates that first message.
- Assess scope before detailed questions: if the request describes multiple independent subsystems (e.g., "a platform with chat, file storage, billing, and analytics"), flag it immediately and don't refine details of a project that needs decomposing first. If it's too large for a single spec, help decompose into sub-projects (independent pieces, how they relate, build order); brainstorm the first one through the normal flow — each sub-project gets its own spec → plan → implementation cycle.
- For appropriately-scoped projects, grill in rounds per `./grilling.md`: the frontier of the decision tree, at most four numbered questions per message, each with a recommended answer; a trivial or reversible change keeps a flat one-or-two-question pass.
- When a question has a small set of fixed answers, present them as a selectable multiple-choice prompt so the user can pick instead of typing (keep a free-text escape). This is the **terminal** path; genuinely visual choices still go through the Visual Companion.
- <a id="stack-fork"></a>**Stack fork — ask it first when nobody knows the stack.** The session bootstrap's `projectProfile` says what this repo is (`stack`, `manifest`). Two states leave the stack unknown: `declared: true` with `stack` empty (onboarding recorded "not decided yet"), or `declared: false` **and** `node <super.using-superpowers-base-dir>/scripts/detect-project.cjs --repo-root <project-repo-root>` answers `detected: false` (no manifest at the root). In either state the stack is a fork the user's phrasing assumes resolved ("an app" is Flutter, React Native or web), so it is the **first** clarifying question — a selectable multiple choice, at most four options, the likeliest first (e.g. **Flutter** · **Node/React** · **Python** · **Other — name it**), and the "not decided" escape when the user wants to hear approaches before choosing. When `projectProfile.stack` is set, or the detector found a manifest, the stack is a **fact**: state it in one clause and move on — never ask what the repo already answers. **Persist the answer the moment it is confirmed**, not at spec time: run `detect-project.cjs --stack <name>`, show its `suggestion` (`stack` + canonical `manifest`), ask "record this profile?", and on yes save it with `node <super.using-superpowers-base-dir>/scripts/write-preferences.cjs --repo-root <project-repo-root>` fed `{ "project": { "stack": "<stack>", "manifest": "<manifest>" } }`. Nothing else goes in `project:` — how the stack is run (test, setup, format) is the repo's instructions file's business, read when a skill needs it. An unconfirmed suggestion is never written; "not decided" leaves the profile as it is and the question returns once the approaches settle it (step 4). The spec's architecture section then names the stack the profile records.
- <a id="framework-fork"></a>**Framework fork — the stack being a fact does not settle the framework.** `projectProfile.stack` names an ecosystem; the ecosystem's web/app framework and its test runner are the next fork the user's phrasing assumes resolved, and they are what every `Run:` line of the plan and the implementer's first file inherit. Read the manifest at `projectProfile.manifest` when it exists: a framework dependency already declared there is a **fact** (state it, never ask), and so is a runner it configures. Greenfield, or a manifest with no framework dependency, makes the framework a clarifying question **before the architecture section** — a selectable multiple choice, at most four options, the recommended one first with its trade-off in one clause each, plus the "no framework / standard library" escape where the ecosystem has one. It is asked, never presented already decided inside the design sections: a framework that first appears as "D1" in an approval gate was chosen by the model, not by the user. The runner is not a question — take the ecosystem's default unless the instructions file or manifest names another — but the spec's Testes section must **name** it: `super.writing-plans` copies the runner from the manifest or the spec and asks when both are silent, never guesses.
- Focus on purpose, constraints, success criteria — **and architecture characteristics**. Use `./architecture-characteristics.md` to translate domain concerns into characteristics ("milhões de usuários" → scalability), surface implicit ones, and put a recommended top 3 to the user — they become the tiebreaker for every later trade-off, so they are asked, never chosen silently.
- <a id="reflect-the-understanding"></a>**Reflect the understanding.** The outcome of the interview is an understanding the user can recognize and correct, grounded in what they want to accomplish — and the app genre never says why they want it ("a todo list" may be a way to learn a framework, a team tool, or a demo; each is a different design). When purpose, audience or success criteria are missing after the first 1-2 answers, ask **one** focused question about purpose or intended use before proposing features or an approach — gathering a missing requirement is not asking the user to authorize the task again. Then write the note: 3-5 lines, one each for the intended outcome, who it is for, what success looks like, the constraints that bind, and a last line **"Assuming:"** listing what you inferred rather than heard. The note is the opening of the approaches question (checklist step 4) — or of an earlier question that already carries it, such as a grilling round asked after the first answers: state it, then ask, so the user corrects the note and answers in one reply. No approach is proposed before the user has seen the note. **A premise every candidate approach shares goes on the "Assuming:" line** — where the data lives, whether it persists, which layer serves it, who the user is: options that all assume it cannot surface it, so the note is the only place the user can flip it ("fictitious data" can mean rows in the real database or no backend at all). Carry the corrected note into the spec's overview — every proposed feature and technical choice is checked against it, and a feature the note does not motivate is a question, not a default. When the request already supplies the purpose and constraints, or `super.deep-research` / the feature-history recall already established them, reflect that understanding in the note instead of asking again; the note is still written, because its accuracy and the chance to correct it are the point.

**Exploring approaches:**

- Propose 2-3 approaches per `./tradeoff-analysis.md`, "Approaches — design it twice".
- Present options conversationally, leading with your recommended option and the reasoning — referencing the trade-off, not just the benefits.

**Presenting the design:**

- Once you believe you understand what you're building, present the design in one message. Scale each section to its complexity: a few sentences if straightforward, up to 200-300 words if nuanced. No per-section approval — the written spec gets one approval gate (SKILL.md step 8).
- Cover the sections the spec will carry (`./design-spec-structure.md`, "Skeleton, scaled to what the interview opened"): scope, characteristics, the approach and its flow, components, boundaries, failures, decisions with trade-offs, risks, testing.
- Derive components with `./logical-components.md`: by the knowledge each one hides, not by execution step, and name the coupling at each boundary.

**Design for isolation and clarity:**

- Break the system into units that each hide one body of knowledge behind a small interface. For each, you should be able to answer: what does it do, how do you use it, what does it depend on?
- Can someone use a unit without reading its internals, and change the internals without breaking consumers? If not, the boundaries need work. Depth matters more than size: a large unit with a small interface beats several thin ones that all know the same format.

**Working in existing codebases:**

- Explore the current structure before proposing changes; follow existing patterns.
- Where existing code has problems that affect the work (a file grown too large, unclear boundaries, tangled responsibilities), include targeted improvements as part of the design — the way a good developer improves code they're working in. Don't propose unrelated refactoring; stay focused on what serves the current goal.
